# Tool 4 — point forecast graph UI — plan

Status: **draft v1, awaiting review.** This covers only the requirements
given so far (model selector, run selector, clickable basemap with the 29
sites, quantity selector with greying-out). More ideas are coming that may
contradict parts of this — expect a v2 revision, not a final spec.

## What this is

A browser tool: pick a model, pick one of its available runs, click a site
on a basemap, and see that site's forecast (temp / cloud total / low / mid
/ high — never rain) as an in-browser chart, for that model+run. Unlike
Tools 1-3 (which browse rendered map PNGs), Tool 4 is entirely numeric —
its source is `data/points.parquet`, not `data/viz/frames/`.

## 1. Data source: `points.parquet`, confirmed shape

```
model:        str
run_init:     datetime[UTC]
member:       int             (-1 = deterministic)
site:         str
valid:        datetime[UTC]
cloud_low/mid/high/total: float | None
temp_c:       float | None
provenance:   str             (native | derived | total_only)
fetched_at:   datetime[UTC]
```

This already has everything Tool 4 needs per point: which quantities exist
for a given (model, run, site) is exactly "which of `temp_c` /
`cloud_total` / `cloud_low` / `cloud_mid` / `cloud_high` is non-null across
that row group" — which is also exactly the greying-out rule (§4).

**Sites in scope for v1: the 29 named places only**, not their WNW-sightline
strip sub-points (`{site}_wnw{25,50,75,100}km`, from `config/sites.yaml`,
expanded at extraction time — see `src/extract/base.py:wnw_strip_points()`).
The strips exist in `points.parquet` under their own `site` values and could
be added later (e.g. a toggle to show them as fainter satellite dots around
their parent site), but the basemap `config/placenames.json` was built for
the 29 named places specifically (`place_count: 29`, no strip points in that
file) - out of scope for v1, flag if wanted.

**Ensemble members**: `points.parquet` carries per-member rows
(`member != -1`) for `aifs_ens`/`ecmwf_ens`. Not addressed in this v1 plan —
picking one model+run for the chart is defined for deterministic models;
what an ensemble model's chart shows (mean line? spaghetti of members? a
band?) needs its own decision and is left open here.

## 2. Data export: a static JSON, not a live query

Every existing tool in this project (Tools 1-3) and the reference UI you
pointed to (`fmi-all-stations`) share one pattern: a static JSON blob,
regenerated by a script, served as a plain file — **no backend, no query
API**. `fmi-all-stations` in particular fetches all-stations data as one
blob and does all filtering/selection client-side.

Proposed: `scripts/generate_tool4_manifest.py` reads `points.parquet`,
writes `tool4_data.json` (or one file per model, if the combined size gets
unwieldy - `points.parquet` is currently a few MB; worth checking the real
number once the rebuild finishes rather than guessing). Shape, one level of
nesting matching the click-to-select flow:

```jsonc
{
  "generated_at": "...",
  "models": {
    "<model_id>": {
      "runs": ["2026080400", "2026080406", ...],       // sorted, what "available runs" populates from
      "sites": {
        "<site_name>": {
          "<run_init>": {
            "valid": ["2026-08-04T00:00Z", ...],
            "temp_c": [12.3, null, ...],
            "cloud_total": [40.0, ...],
            "cloud_low": [...], "cloud_mid": [...], "cloud_high": [...]
          }
        }
      }
    }
  }
}
```

Open question, not decided here: whether to cap history the same way the
just-built frame retention does (newest N runs/model) so this file doesn't
grow unbounded as more runs accumulate - `points.parquet` itself isn't
pruned today. Flagging, not deciding.

## 3. The basemap — genuinely new territory, needs a decision

This is the one piece with **no existing precedent to extend**. Researched
directly before writing this plan:

Tools 1-3's basemap (`src/viz/basemap.py`'s `draw_basemap()` — coastlines +
roads from Natural Earth, called from `frame_renderer.py`) is drawn
**server-side, baked into the rendered PNG**. No vector coastline/road/
totality-path data ever reaches the browser today. A clickable, per-site
basemap is a different requirement entirely - it needs the geometry as
data the browser can hit-test against, not a flat image.

Two ways to get there:

**Option A - vector map, client-side** (matches `fmi-all-stations`'
approach: it ships a small pre-baked Finland GeoJSON and draws stations as
SVG dots with real hit targets). Would need a one-time export of simplified
coastline + roads + totality band, clipped to the Iberia bbox, from the
same Natural Earth data `basemap.py` already caches
(`DATA_ROOT/cache/naturalearth/`), as GeoJSON or raw SVG path data. Site
markers are then real SVG/DOM elements - trivially clickable, easy to
highlight on hover exactly like the reference project's linked map/chart
hover.

**Option B - raster basemap + absolutely-positioned overlay markers.**
Render one plain basemap PNG (coastlines + roads + totality, no cloud
data - `basemap.py` already does the coastline/road/totality part of this,
would just need a frame with nothing else on it) and place the 29 site
markers as an HTML overlay, positioned via the bbox-to-pixel math
`frame_renderer.py` already has for its own figure layout
(`_figure_layout`, lines ~930-947). Cheaper to build, but more fragile
(exact overlay alignment across different screen sizes/DPI needs care) and
markers aren't part of the same coordinate system as anything else.

**Leaning toward Option A**, since it's what the reference project actually
does and gives real interactivity (hover-highlight, not just click) for
free - but this is exactly the kind of thing worth confirming before
building, given it's the one part with no existing code to lean on.

## 4. UI layout (per your description)

- **Model selector** - list box, populated from the manifest's `models`
  keys.
- **Run selector** - list box, populated from the selected model's `runs`
  list (re-populated on model change).
- **Basemap** - coastlines, roads, totality band (matching Tools 1-3's
  visual language), 29 site markers. Click a marker to select that site.
- **Quantity selector** - temp / total / low / mid / high (never rain, per
  your explicit exclusion). Once a model+run+site is selected, grey out
  whichever quantities are all-null for that combination (e.g. `ecmwf_ens`
  has no temp at all per its `surface_temp.enabled: false` cost opt-out in
  `models.yaml`; some models have no native low/mid/high, only total).
- **Chart** - populated once a site is clicked; updates in place as
  model/run/quantity change without needing a re-click.

## 5. Charting library

Recommend **uPlot**, matching the reference project exactly: vendored
locally (no CDN dependency, ~51 KB), proven at this data scale, and its
linked-hover / pin-to-compare interaction model is a good fit if Tool 4
later grows a "compare sites" or "compare runs" mode (your stated intent to
layer on more ideas). No other charting library is used anywhere else in
this project yet, so this would be Tool 4's own new dependency either way -
matching a working reference beats picking a new one from scratch.

## 6. Serving

No new infrastructure needed: `scripts/serve_frames.py`'s existing static
file server already serves whatever sits under `data/viz/frames/` (or
wherever this gets placed) with correct caching behavior
(`_NO_CACHE_NAMES` already treats manifests/HTML as always-revalidate).
Tool 4's HTML/JS/JSON just needs to land in that served tree, same as
Tools 1-3.

## 7. Explicitly not decided here

- The basemap approach (§3 Option A vs B).
- Whether/how ensemble models (`aifs_ens`, `ecmwf_ens`) get a chart at all.
- Whether the WNW-strip points get any UI representation.
- History cap on the exported JSON (§2).
- Your additional ideas, not yet described.

## 8. Rollout sketch (once the above is settled)

1. Build `scripts/generate_tool4_manifest.py` against the rebuilt
   `points.parquet` (in progress as of this plan's writing).
2. Build the basemap asset (§3's chosen option) - one-time export, not
   per-request.
3. Build the static HTML/JS client (model/run selectors, basemap markers,
   uPlot chart, quantity greying-out).
4. Wire into `serve_frames.py`'s tree, verify in browser against real data.
